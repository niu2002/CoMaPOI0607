# CoMaPOI 协同多 Agent POI 预测评测报告与学术分析 (CA数据集)

本文件整合了在 CA 数据集（101 个测试样本）上运行的纯 API 对照实验指标，深入分析了云端 RAG 检索机制对系统精度的实际贡献，探讨了 API Token 资金消耗的根源，并给出了远程 AMD 算力服务器上最高效的“云端-本地混合部署”策略建议。

### 1.2 核心机制发现：“信息稀释与黄金候选挤占假说” (Information Dilution & Candidate Crowding Out)

对照实验表明，在 Top-5 和 Top-10 召回中，不使用 RAG 的 **方案 B** 反而明显胜出（HR@10 达到了 **39.60%**，比方案 A 高出近 3 个百分点）。我们从协同多 Agent 和 RRF 融合机制的角度提出以下理论假说：

1. **用户出行意图的极强时空地缘粘性 (Spatio-Temporal Locality)**：
   在下一步 POI 预测中，用户的下一次签到高度集中在其**最近访问过的 POI（Recency）**、**频繁重复的 POI（Frequency）**或**当前物理坐标邻近的 POI（Proximity）**中。在互易排名融合 (RRF) 时，`history_recent`（权重 1.2）和 `history_freq`（权重 1.0）包含着召回的“黄金答案”。
2. **100 个 RAG 语义候选池的干扰**：
   方案 A 中引入的 `rag_top100`（包含 100 项）是由向量模型（`text-embedding-v3`）基于轨迹文本描述与 POI 文本描述之间的余弦相似度检索得到的：
   \[ \text{Similarity} = \frac{\mathbf{v}_q \cdot \mathbf{v}_p}{\|\mathbf{v}_q\| \|\mathbf{v}_p\|} \]
   虽然这些候选在**语义范畴**上与轨迹相似（如同样是咖啡馆），但在实际空间运动中大多并非用户的物理目的地，因此它们构成了大体量的“语义噪声”。
3. **RRF 挤占机制**：
   在进行 RRF 融合时，分数的计算公式为：
   \[ RRF(p) = \sum_{m \in S} \frac{w_m}{k + \text{rank}_m(p)} \]
   因为 `rag_top100` 的基数非常庞大且权重（1.0）较高，当最终输入池被强制截断到前 50 项（`fused_candidate_top_k=50`）时，许多原本在历史和邻近源中处于中后排、但其实正确的黄金目标被大量低关联度的 RAG 噪声候选**挤出了融合候选池**。
4. **Agent 3 的无米之炊**：
   最终决策模型 Agent 3 (Final Predictor) 只能从这 50 个被污染的候选池中进行二次推理和排序。一旦黄金目标已经跌出前 50，Agent 3 将彻底失去将其预测正确的机会，导致 Top-5/10 召回率显着下降。

## 2. API Token 资金消耗审计分析

从百炼监控面板展示的总用量来看：
* **调用成功总次数**：4,834 次
* **Token 总消耗量**：33,516K tokens（约 3350 万 tokens）
* **消耗金钱的绝对主力（罪魁祸首）**：**`qwen-plus` 决策大模型**。

### 2.1 消耗占比分析
1. **`qwen-plus` (Top 1 / 2,598 次调用)**：
   * 在前向推理中，每个测试样本都需要串行调用 3 个 Agent（Profiler 画像提取、Forecaster 意图预测、Predictor 决策重排）。
   * 为了给大模型足够的画像推理上下文，我们的 Prompt 引入了较长的历史轨迹事件，使得单次请求的 Prompt Token 数普遍在数千级别（平均单次请求达 6,934 tokens）。
   * 2,598 次调用累积消耗了约 **18M tokens**。按 `qwen-plus` 的官方价格计算，这部分开销占了整体账单的 **95% 以上**！
2. **`text-embedding-v3` (Top 2 / 2,135 次调用)**：
   * 虽然有 2,135 次调用，但百炼的 Embedding 计费极低，且每次请求体非常小（总共仅消耗约 1.5M tokens），这部分的总花费一般不超过 1 元人民币，并非费用超支的主因。
3. **`qwen-rerank` (Top 3 / 101 次调用)**：
   * 仅用于 101 个样本的重排，费用占比极小（小于 1%）。

## 3. 远程 AMD 服务器“云端-本地”最佳混合部署推荐

为了在远程服务器（AMD 端）以最低的 API 资金开销获得最高的评测精度（@5, @10），我们建议采用 **云端 API（Agent 1 & 2） + 本地微调 LoRA（Agent 3）** 的混合模式：

### 3.1 三个 Agent 的部署模式推荐
* **Agent 1 (Profiler) -> 云端 API (`qwen-plus`)**：
  * **原理解析**：Profiler 的任务是提炼用户画像。这需要模型对签到地点进行高级别的**语义抽象和画像归纳**。这属于通用的“零样本常识总结”，需要极强的大模型理解能力。若用本地 8B 级别的基座运行，极易产生语义退化或复读，影响下游推理。
* **Agent 2 (Forecaster) -> 云端 API (`qwen-plus`)**：
  * **原理解析**：Forecaster 的任务是进行短期意图模式预测和 RAG 精炼。这也极度依赖大模型的通用逻辑推理和时空模式推理，使用云端 API 能够提供最稳健、逻辑最清晰的分析输出。
* **Agent 3 (Predictor) -> 本地 LoRA 微调（基于 Modelscope 载入的 `Qwen2.5-7B-Instruct`）**：
  * **原理解析**：Predictor 的核心任务是针对前 50 个融合候选进行重排与最终预测。
  * **为什么它的 @5, @10 指标会最好？**：
    1. **专门领域的逆向微调增益**：Agent 3 已经使用 300 条由 `paper_label_first_fused` 逆向微调的 LoRA 适配器进行了深度域自适应学习。它专门学习了如何整合 Agent 1 & 2 的画像并在融合候选池中寻找匹配规律。其领域准确度能达到或超越通用云端 API 模型。
    2. **物理截断对齐**：Agent 3 的输入长度和逻辑已经高度针对 8B 模型和特定的微调模板进行了裁剪，在预测特定 POI ID 时，本地微调模型的输出规范性要强于云端 API 的自由生成。
    3. **零 Token 开销与高速推理**：在 AMD 服务器（利用 vLLM 和 ROCm 显卡加速）上部署 Agent 3 本地服务，不仅完全免费，而且其高并发推理速度将大幅缩减全量评测的耗时。
