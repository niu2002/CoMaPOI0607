# 两个创新点提取与落地实验方案：HSID + ExpertRAG

> 来源说明：`paper_summary.md` 是原 CoMaPOI 论文整理；`hsid_expertrag_zh.pdf` 是在原论文结构上加入两个新创新点后的版本。本文只抽取其中两个新增点：**语义 ID / HSID** 与 **ExpertRAG**，并说明如何在你现在的 CoMaPOI 代码上做实验。

---

## 一、创新点 1：语义 ID / HSID（Hierarchical Semantic ID）

### 1.1 简单思想

原 CoMaPOI 里，POI 主要以普通 ID、经纬度、类别文本等形式进入 RAG 检索和 Agent Prompt。这个设计的问题是：

- POI ID 是离散符号，`poi_123` 和 `poi_456` 即使在同一商圈、同一类别，模型也很难天然知道它们相关；
- 长尾 POI 或签到很少的 POI 缺乏训练样本，模型很难学到稳定表示；
- RAG 只靠单条 POI 文本相似度时，容易忽略“同区域、同功能、同层级语义”的共享信息。

**HSID 的核心思想**：给每个 POI 额外构造一个多层语义编码，不替代原 POI ID，而是作为 POI ID 外面的“语义支架”。例如：

```text
POI 原 ID:  8f3a2
HSID:       region=R12, subregion=R12_07, category=Food, semantic_cluster=C043
```

这样模型不仅知道它是某个具体 POI，还知道它属于哪个大区域、小区域、功能类别和细粒度语义簇。对稀疏 POI 来说，可以借助同区域、同类别、同语义簇的 POI 迁移知识。

### 1.2 相比原 CoMaPOI 的新增点

原 CoMaPOI 已经有：

- Profiler Agent：把用户历史和当前轨迹转成画像与移动模式；
- Forecaster Agent：基于 RAG 初筛候选，再根据长期画像、短期模式精排；
- Predictor Agent：在候选集上做最终预测；
- RRF：用真实下一 POI 反向构造中间监督。

HSID 不改变这个三 Agent 主流程，而是在三个位置增强它：

1. **RAG 检索文本增强**：POI 描述中加入 HSID 层级信息，使相似 POI 更容易被召回。
2. **Prompt 候选信息增强**：候选列表中不仅展示 POI ID、类别、坐标，也展示区域、子区域、语义簇。
3. **训练数据增强**：SFT / RRF 样本里加入 HSID 字段，让 Agent 学会利用层次语义进行筛选和解释。

### 1.3 HSID 怎么构建

建议先做轻量、可复现版本，不要一开始就做复杂神经编码。每个 POI 构造 4 层即可：

| 层级 | 名称 | 构造方式 | 作用 |
|---|---|---|---|
| Level 1 | coarse_region | 经纬度粗网格、GeoHash、H3 粗分辨率 | 表示大范围地理区域 |
| Level 2 | fine_region | 经纬度细网格、GeoHash、H3 细分辨率 | 表示附近街区/局部区域 |
| Level 3 | category | 数据集已有 POI 类别 | 表示功能语义 |
| Level 4 | semantic_cluster | 用 POI 文本/类别/坐标 embedding 做 KMeans，或用 `category + fine_region` 组合 | 表示更细粒度的语义簇 |

输出文件建议为：

```text
data/<dataset>/poi_hsid.json
```

示例格式：

```json
{
  "8f3a2": {
    "coarse_region": "R_034",
    "fine_region": "R_034_118",
    "category": "Food",
    "semantic_cluster": "SC_043",
    "hsid_text": "coarse_region=R_034; fine_region=R_034_118; category=Food; semantic_cluster=SC_043"
  }
}
```

### 1.5 HSID 实验怎么做

HSID 实验建议分成“无模型候选召回实验”和“有 LLM forward 实验”。先不训练，先看候选召回是否提升。

#### 实验 H0：原始 baseline

目的：作为对照组。

```bash

  --mode test \
  --num_samples 101 \
  --top_k 100

python ops/analyze_candidate_recall.py \
  --dataset ca \
  --mode test \
  --num_samples 101 \
  --strategy rrf \
  --fused_candidate_top_k 100
```

记录：

```text

HR@1 / HR@5 / HR@10 / MRR / NDCG@10
```

#### 实验 H1：只把 HSID 加进 RAG 文本

目的：验证 HSID 是否能改善候选召回。

```bash
python ops/build_candidates_amd.py \
  --dataset ca \
  --mode test \
  --num_samples 101 \
  --top_k 100 \
  --use_hsid \
  --hsid_path data/ca/poi_hsid.json \

  --candidate_file outputs/candidates/ca_test_101_hsid_rag_top100.jsonl \
  --fused_candidate_top_k 100
```

判断标准：如果 `RAG@100` 或 `all_union@100` 明显提升，说明 HSID 对召回有效。

#### 实验 H2：RAG 不变，只把 HSID 加进 Predictor Prompt

目的：验证 HSID 是否帮助 LLM 在已有候选里排序。

做法：候选文件用 H0 原始候选；只修改 `prompt_provider.py`，让候选展示带 HSID。

```bash
bash ops/run_forward_101_amd.sh
python ops/analyze_forward_results.py --dataset ca --num_samples 101
```

判断标准：候选召回不变，但 HR@10、MRR、NDCG@10 提升，说明 HSID 主要帮助排序。

#### 实验 H3：HSID-RAG + HSID-Prompt

目的：验证完整 HSID 效果。

做法：同时使用 H1 的 HSID 候选和 H2 的 HSID Prompt。

推荐命名：

```text
exp_hsid_rag_prompt_101
exp_hsid_rag_prompt_500
exp_hsid_rag_prompt_full
```

先跑 101，再跑 500，最后再考虑 full。

#### 实验 H4：HSID 分层消融

目的：证明不是“多加文本就提升”，而是层次结构有效。

消融组：

| 组别 | 使用字段 |
|---|---|
| H4-a | only original POI ID |
| H4-b | POI ID + category |
| H4-c | POI ID + coarse_region + fine_region |
| H4-d | POI ID + category + semantic_cluster |
| H4-e | POI ID + all HSID levels |

重点看：

```text
candidate recall@100
HR@10
NDCG@10
long-tail POI subset HR@10
```

#### 实验 H5：长尾 POI 分析

目的：证明 HSID 对稀疏、长尾 POI 更有价值。

按训练集中 POI 出现次数分桶：

```text
0-2 次：极稀疏
3-5 次：稀疏
6-10 次：中低频
>10 次：高频
```

比较 baseline 与 HSID 在不同桶上的 HR@10 / NDCG@10。

### 1.6 HSID 预期结果

HSID 最可能带来的提升顺序是：

```text
长尾 POI 表现提升 > 候选召回提升 > 最终 HR@10 小幅提升
```

如果最终 HR@10 没明显提升，也要看两个中间指标：

1. `candidate recall@100` 是否提升；
2. 正确答案已经在候选集内时，`candidate-inside accuracy / HR@10` 是否提升。

如果召回提升但最终 HR@10 不提升，说明 Predictor 没利用好 HSID，需要加强 Prompt 或训练样本。

## 二、创新点 2：ExpertRAG（多专家检索增强）

### 2.1 简单思想

原 CoMaPOI 的候选生成主要依赖单路 RAG 初筛，再交给 Forecaster Agent 按长期画像和短期模式重排。问题是：真实出行意图是异质的，不同样本需要不同检索逻辑。

例如：

- 通勤场景：下一 POI 通常和最近位置、历史转移路径强相关；
- 饭点消费：时间段和类别偏好更重要；
- 探索访问：语义相似、区域相近、类别相关更重要；
- CA 这种大地理范围数据：单纯语义 RAG 很容易召回不到真实 POI。

**ExpertRAG 的核心思想**：不要只用一个 RAG 检索器，而是构造多个互补专家，每个专家负责一种候选召回逻辑，然后用路由网络或启发式权重根据当前轨迹动态融合。

建议先实现 4 个专家：

| 专家 | 作用 | 候选来源 |
|---|---|---|
| spatial expert | 地理可达性 | 距离最近位置、用户活动中心、历史区域最近的 POI |
| transition expert | 序列转移规律 | 训练集中 `prev_poi -> next_poi`、`prev_category -> next_category` 转移统计 |
| temporal expert | 时间偏好 | 同小时、同星期、同时间段高频访问 POI / 类别 |
| semantic expert | 语义相似性 | 原 RAG embedding、HSID 相似、类别相似 |

最终不是简单 union，而是：

```text
每个专家 topK0 候选 -> 分数归一化 -> router 生成专家权重 -> 融合排序 -> topK 最终候选
```

### 2.2 相比原 CoMaPOI 的新增点

原 CoMaPOI 的 Forecaster 更像是：

```text
单路 RAG 初筛 -> LLM 根据长期画像/短期模式重排
```

ExpertRAG 改成：

```text
空间专家 + 转移专家 + 时间专家 + 语义专家
          ↓
     动态路由 / 加权融合
          ↓
    高召回、高相关候选集
          ↓
 Predictor / Agent3 排序
```

它主要解决你当前实验里最关键的问题：**label 不在候选池时，后续 Agent3 无法补救**。因此 ExpertRAG 应该优先做候选召回诊断，不要一上来训练 LoRA。

### 2.3 各专家如何实现

#### 2.3.1 Spatial Expert：空间专家

输入：最近一个 POI、当前轨迹平均位置、用户历史活动中心。

候选：

```text
last_poi 附近 topK0 POI
current trajectory centroid 附近 topK0 POI
user historical centroid 附近 topK0 POI
```

分数示例：

```text
score_spatial(p) = - haversine_distance(last_location, p.location)
```

可加衰减：

```text
score_spatial(p) = - min_distance_to_recent_pois(p) + repeat_bonus(user, p)
```

#### 2.3.2 Transition Expert：转移专家

从训练集统计：

```text
count(prev_poi, next_poi)
count(prev_category, next_poi)
count(prev_category, next_category)
```

分数示例：

```text
score_transition(p) = log(1 + count(last_poi -> p))
                    + alpha * log(1 + count(last_category -> p.category))
                    + beta  * log(1 + count(recent_category_seq -> p.category))
```

如果 POI 级转移太稀疏，就退化到 category 级、region 级或 HSID 级转移。

#### 2.3.3 Temporal Expert：时间偏好专家

按目标预测时间提取：

```text
hour
weekday
is_weekend
time_bucket: morning / noon / afternoon / evening / night
```

统计：

```text
P(poi | hour)
P(category | hour)
P(region | hour)
P(poi | user, hour)    # 如果用户样本足够
```

分数示例：

```text
score_temporal(p) = log P(p.category | target_hour)
                  + log P(p.region | target_hour)
                  + user_time_bonus(u, p, target_hour)
```

#### 2.3.4 Semantic Expert：语义专家

这是原 RAG 的增强版。候选来源可以有三类：

```text
1. Qwen3-Embedding / BCE embedding 的原始语义相似候选
2. HSID 层次相似候选
3. 同 category / semantic_cluster 的高频或近邻 POI
```

HSID 相似度示例：

```text
kappa(p_i, p_j) = 1[coarse same] * w1
                + 1[fine same]   * w2
                + 1[category same] * w3
                + 1[cluster same]  * w4
```

语义专家分数：

```text
score_semantic(p) = cosine(context_embedding, poi_embedding)
                  + gamma * hsid_similarity(recent_pois, p)
```

### 2.4 Router 怎么实现

先做启发式 router，后做学习式 router。

#### 版本 A：启发式 router，最快能跑实验

根据当前轨迹特征给专家权重：

```python
def route_weights(sample):
    features = extract_features(sample)
    # features: avg_recent_distance, repeat_ratio, category_entropy, hour, has_known_transition

    w = {
        "spatial": 1.0,
        "transition": 1.0,
        "temporal": 1.0,
        "semantic": 1.0,
    }

    if features["avg_recent_distance"] < 2.0:
        w["spatial"] += 0.5

    if features["has_known_transition"]:
        w["transition"] += 0.8

    if features["hour_pattern_strong"]:
        w["temporal"] += 0.5

    if features["category_entropy"] > 1.5:
        w["semantic"] += 0.5

    return softmax(w)
```

#### 版本 B：学习式 router，论文感更强

训练一个轻量 MLP 或 Logistic Router：

```text
输入：当前轨迹统计特征 + 长期用户统计特征
输出：4 个专家权重
目标：让真实 POI 在融合分数中排名更靠前
损失：cross entropy / pairwise ranking loss / retrieval alignment loss
```

但你现在最需要先把召回做上去，所以建议第一阶段先用启发式 router + RRF 融合。

#### Step 2：新增 ExpertRAG 候选生成模块

新增：

```text
expertrag.py
```

核心接口建议：

```python
class ExpertRAG:
    def retrieve(self, sample, top_k0=100, final_top_k=100):
        spatial = self.spatial_expert(sample, top_k0)
        transition = self.transition_expert(sample, top_k0)
        temporal = self.temporal_expert(sample, top_k0)
        semantic = self.semantic_expert(sample, top_k0)

        weights = self.router(sample)
        candidates = self.fuse(
            expert_outputs={
                "spatial": spatial,
                "transition": transition,
                "temporal": temporal,
                "semantic": semantic,
            },
            weights=weights,
            final_top_k=final_top_k,
        )
        return candidates
```

候选输出建议保留专家证据：

```json
{
  "sample_id": "...",

        "spatial": 0.92,
        "transition": 0.11,
        "temporal": 0.40,
        "semantic": 0.76
```

#### Step 3：改造 `candidate_fusion.py`

现有 `candidate_fusion.py` 可以继续用，但要支持多专家分数。

融合方式建议两种都做：

1. **RRF 融合**：不依赖分数尺度，稳定。

```text
score(p) = Σ_m 1 / (k + rank_m(p))
```

2. **Router 加权融合**：更贴近 ExpertRAG。

```text
score(p) = Σ_m router_weight_m * normalized_score_m(p)
```

注意：不同专家分数尺度不同，必须先归一化。

```python
def normalize(scores):
    # 可用 z-score，也可用 min-max 或 rank percentile
    return (scores - mean(scores)) / (std(scores) + 1e-6)
```

```text
Evidence: retrieved by spatial and semantic experts.
```

### 2.6 ExpertRAG 实验怎么做

#### 实验 E0：原始 RAG / 当前 baseline

记录你当前已有 baseline：

```text
base-only 101 HR@10
MRR
NDCG@10
candidate recall@100
```

这个是后面对比的锚点。

#### 实验 E1：单专家召回诊断，不启 LLM

目的：先看每个专家本身有没有用。

分别输出：

```text
spatial_top100.jsonl
transition_top100.jsonl
temporal_top100.jsonl
semantic_top100.jsonl
```

分析：

```bash
python ops/analyze_candidate_recall.py \
  --dataset ca \
  --mode test \
  --num_samples 101 \
  --candidate_file outputs/candidates/ca_test_101_spatial_top100.jsonl
```

记录表格：

| 候选来源 | Recall@10 | Recall@25 | Recall@50 | Recall@100 |
|---|---:|---:|---:|---:|
| original RAG |  |  |  |  |
| spatial expert |  |  |  |  |
| transition expert |  |  |  |  |
| temporal expert |  |  |  |  |
| semantic expert |  |  |  |  |

如果某个专家很弱，不要马上删掉，因为它可能对某些子场景有效。后面看路由和消融。

#### 实验 E2：专家 union 召回

目的：看理论上多专家能不能覆盖更多真实答案。

```bash
python ops/build_candidates_amd.py \
  --dataset ca \
  --mode test \
  --num_samples 101 \
  --top_k 100 \
  --strategy expertrag_union \
  --expert_index_dir data/ca/expert_indexes \
  --output outputs/candidates/ca_test_101_expertrag_union_top100.jsonl
```

如果 `expert_union@100` 明显高于原始 RAG@100，说明方向对。

#### 实验 E3：RRF 融合 vs Router 融合

目的：证明动态路由不是多余的。

对比：

| 组别 | 融合方式 |
|---|---|
| E3-a | expert union，按来源顺序截断 |
| E3-b | RRF 融合 |
| E3-c | uniform weighted fusion |
| E3-d | heuristic router weighted fusion |
| E3-e | learned router weighted fusion，可后做 |

指标：

```text
Recall@25 / Recall@50 / Recall@100
平均候选数
label_missing
```

重点看 `Recall@50` 和 `Recall@100`，因为后续 Predictor 的输入不能无限变大。

#### 实验 E4：ExpertRAG + Predictor Prompt，不训练

目的：验证多专家候选是否能提升最终 forward 指标。

```bash
python ops/build_candidates_amd.py \
  --dataset ca \
  --mode test \
  --num_samples 101 \
  --top_k 100 \
  --strategy expertrag \
  --expert_index_dir data/ca/expert_indexes \
  --output outputs/candidates/ca_test_101_expertrag_top100.jsonl

bash ops/run_forward_101_amd.sh
python ops/analyze_forward_results.py --dataset ca --num_samples 101
```

这里要保证 `inference_forward_new.py` 读取的是 ExpertRAG 候选文件，而不是旧候选文件。

#### 实验 E5：ExpertRAG + Agent2/Agent3

目的：验证原论文多 Agent 流程里加入 ExpertRAG 后是否更好。

关键原则：**Agent2 不要强过滤**。如果 Agent2 把真实 label 过滤掉，Agent3 再强也没用。

建议让 Agent2 做：

```text
补充解释 + 重排 + 打分
```

不要做：

```text
强制从 100 个候选删到 10 个
```

更稳妥做法：

```text
ExpertRAG top100 -> Agent2 rerank top50 -> Agent3 final top10
```

或者：

```text
ExpertRAG top100 -> Agent2 给每个候选附理由/分数 -> Agent3 看 top50 + evidence
```

#### 实验 E6：去掉单个专家的消融

目的：证明每个专家都有贡献。

| 组别 | 设置 |
|---|---|
| Full ExpertRAG | spatial + transition + temporal + semantic |
| w/o spatial | 去掉空间专家 |
| w/o transition | 去掉转移专家 |
| w/o temporal | 去掉时间专家 |
| w/o semantic | 去掉语义专家 |
| no router | 专家等权 |
| no evidence prompt | Prompt 不展示专家证据 |

记录：

```text
candidate recall@100
HR@10
MRR
NDCG@10
```

#### 实验 E7：候选集大小敏感性

目的：找最合适的 final_top_k。

```text
K = 25, 50, 75, 100, 150
```

原论文里候选太大可能会引入噪声，因此不要只追求 Recall@100，也要看最终 HR@10 / NDCG@10。

#### 实验 E8：HSID + ExpertRAG 联合实验

目的：证明两个创新点不是重复的。

对比四组：

| 组别 | HSID | ExpertRAG |
|---|---|---|
| baseline | 否 | 否 |
| HSID only | 是 | 否 |
| ExpertRAG only | 否 | 是 |
| HSID + ExpertRAG | 是 | 是 |

如果结果是：

```text
HSID only > baseline
ExpertRAG only > baseline
HSID + ExpertRAG > 两个单独组
```

就可以写成两个创新点互补：

```text
HSID 负责增强 POI 表示和语义共享；ExpertRAG 负责针对不同出行意图自适应召回候选。
```

### 2.7 推荐实验顺序

不要直接跑 full，也不要先训练 LoRA。推荐顺序：

```text
1. 101 样本：HSID 构建是否正确
2. 101 样本：单专家 candidate recall
3. 101 样本：ExpertRAG union / RRF / router recall
4. 101 样本：base-only forward
5. 500 样本：重复最优的 2 到 3 个设置
6. full CA：只跑最终最优设置
7. 如果候选召回稳定提升，再做 Agent2/Agent3 LoRA 或 RRF 训练
```

当前你最应该优先看的不是最终 HR@10，而是：

```text
label 是否在候选池里
candidate recall@50 / @100 是否提升
Agent2 是否误删 label
```

### 2.8 最小可行版本（MVP）

如果只想最快验证两个创新点，建议做这个最小版本：

```text
MVP-1：build_hsid.py
  生成 coarse_region / fine_region / category / semantic_cluster

MVP-2：HSID-RAG
  把 hsid_text 拼进 POI embedding 文本

MVP-3：ExpertRAG-lite
  spatial expert + transition expert + original semantic RAG
  先不做 learned router，只做 RRF 融合

MVP-4：Prompt evidence
  候选里展示 HSID 和 top-2 expert sources

MVP-5：101 forward
  跑 HR@10 / MRR / NDCG@10
```

MVP 的目标不是一步达到论文指标，而是证明：

```text
候选召回变高，且最终 forward 不下降。
```

只要这两个成立，再继续加 temporal expert、router 和训练损失。

## 三、最终论文/报告里可以怎么表述

### 3.1 HSID 的论文表述

> We introduce a lightweight Hierarchical Semantic ID for each POI, which encodes multi-level geographical and functional semantics such as coarse region, fine region, category, and semantic cluster. Instead of replacing the original POI identifier, HSID complements it with structured semantic information, enabling knowledge sharing among geographically close or functionally similar POIs and improving robustness for sparse and long-tail locations.

中文：

> 本文为每个 POI 构建轻量级层次语义标识 HSID，将粗粒度区域、细粒度区域、功能类别和语义簇编码为多层结构。HSID 不替代原始 POI ID，而是在其基础上提供结构化语义支架，使模型能够在地理相近或功能相似的 POI 之间共享知识，从而缓解长尾 POI 和稀疏轨迹场景下的泛化问题。

### 3.2 ExpertRAG 的论文表述

> We propose an ExpertRAG module that decomposes candidate retrieval into multiple complementary experts, including spatial, transition, temporal, and semantic experts. A context-aware router dynamically aggregates expert evidence according to the current trajectory state, producing a compact candidate set with higher coverage and relevance than single-source RAG retrieval.

中文：

> 本文提出 ExpertRAG 多专家检索模块，将候选生成分解为空间可达性、序列转移、时间偏好和语义相似四类互补专家。路由网络根据当前轨迹上下文动态融合不同专家证据，从而生成比单一路 RAG 更高覆盖、更高相关性的紧凑候选集。
